## Spend cap: the tests behind the PROVEN row

The spend guard admits a downstream payment only while `settled + reserved + unresolved + amount` stays within the job's maximum, and the job maximum can never exceed the absolute cap of 5.00 USDC. The reservation is a single conditional `UPDATE` in the same database transaction that records the payment, so parallel attempts cannot overspend. These tests exercise it and all pass in [`evidence/g3-test-suite.txt`](evidence/g3-test-suite.txt):

- `packages/core/tests/spend-guard-simulation.test.ts` — "A16 (pure): no sequence of guarded reservations exceeds the job cap" (randomised reserve / settle / release / unresolve, seeds 1, 7, 42, 2026, 5,000 steps each).
- `packages/core/tests/spend-guard.test.ts` — "allows spending exactly at the scenario, job, and absolute caps" and "denies one micro over the scenario, job, or absolute cap".
- `apps/api/tests/ledger/concurrency.test.ts`, against a real PostgreSQL database:
  - "A16: three parallel 0.05 reservations against a 0.10 job reserve exactly two"
  - "A16: thirty parallel mixed-size reservations against 0.50 never overspend"
  - "A16: randomised reserve/settle/release/unresolve interleaving with seed 1 / 7 / 42 / 2026"
- `apps/api/tests/preflight/preflight.test.ts` — "A11 (preflight): a target priced above the job budget is ineligible".

This proves the cap in code and against a real database. It does not by itself prove anything about a live Mainnet job.

## How a claim becomes PROVEN

A claim moves to PROVEN only when a sanitized artifact from a real run is saved under [`docs/evidence/`](evidence/README.md) and linked in the Evidence column. The artifact is produced by the commands described in the evidence index, never written by hand, and never contains a mnemonic, private key, signed payment payload or bearer credential. Transaction IDs in an artifact can be checked independently on an Algorand explorer. If a later run contradicts an artifact, the claim goes back to NOT PROVEN until new evidence is captured.
